# Personal Assistant — CONTRIBUTING

**Статус: WORKING BASELINE v1.0 · 27.11.2026.** Робочий технічний контракт, зафіксований SM для розблокування SET-02 та паралельної розробки. Рішення v1.0 прийнято без попереднього погодження всіма учасниками; коментарі TL/DEV A/DEV B опрацьовуємо окремими змінами без зупинки сумісної роботи. Вимоги ТЗ і TECH мають пріоритет. Після публікації в `main` саме версія у `main` є єдиним джерелом технічних домовленостей.

## 1. Контекст і scope (вимоги)

CLI Personal Assistant: контакти (ім'я, адреса, телефон, email, день народження; створення, пошук за різними критеріями, редагування, видалення; перевірка телефону/email при створенні й редагуванні; список днів народження через задану кількість днів); текстові нотатки (створення, пошук, редагування, видалення); усі дані на диску в папці користувача, відновлення після перезапуску. Додатково: теги, пошук і сортування за тегами; пропозиція найближчої команди за введеним текстом. Ціль — усі вимоги для 100 балів, не гарантія оцінки.

TECH: CLI у циклі до виходу; меню на старті, далі за `help`; читабельність, помилки вводу не завершують програму; ООП, спадкування, композиція, валідація кожного поля, PEP 8, коментарі й документація, README, mentor review. Джерела: ТЗ XLSX A8–A18, A24–A27; TECH п. 1–14 та додаткові п. 1–2; План роботи, с. 1–4.

## 4. Робочі контракти (SET-02 синхронізує з skeleton)

### Models (без input/print/storage)

- `Field(value)`; `Name`, `Address`, `Phone`, `Email`, `Birthday` наслідують `Field`. `Contact` використовує поля через композицію; `AddressBook` містить контакти.
- `Contact`: `name: str`, `address: str | None`, `phone: str | None`, `email: str | None`, `birthday: date | None` як зовнішні значення; внутрішньо можуть бути Field objects. `to_dict() -> dict`, `from_dict(data) -> Contact`.
- `AddressBook.add_contact(name, *, address=None, phone=None, email=None, birthday=None) -> Contact`; `get_contact(name) -> Contact`; `list_contacts() -> list[Contact]`; `update_contact(name, /, **changes) -> Contact`; `delete_contact(name) -> None`; `search_contacts(query, *, field="name") -> list[Contact]`; `upcoming_birthdays(days, *, today=None, exact=False) -> list[tuple[Contact, date]]`; `to_dict() -> list[dict]`, `from_dict(data) -> AddressBook`.
- **Уточнення v1.0:** у `update_contact` старе ім’я передається лише позиційно, нове — як `name` у `changes` (наприклад, `book.update_contact("Anna", name="Hanna")`). Зберігаються правила унікальності й атомарності валідації. Виклики зі старим ім’ям як keyword argument необхідно адаптувати. Тип результату не змінюється.
- `Note`: `id: str`, `text: str`, `tags: list[str]`; `to_dict() -> dict`, `from_dict(data) -> Note`. `NoteBook` містить нотатки.
- `NoteBook.add_note(text) -> Note`; `get_note(note_id) -> Note`; `list_notes() -> list[Note]`; `update_note(note_id, text) -> Note`; `delete_note(note_id) -> None`; `search_notes(query) -> list[Note]`; `add_tags(note_id, tags) -> Note`; `find_by_tag(tag) -> list[Note]`; `sort_by_tags(tags) -> list[Note]`; `to_dict() -> list[dict]`, `from_dict(data) -> NoteBook`.
- Для помилок вводу/дублікатів/невідомого ключа — `ValueError` з коротким повідомленням. Не змінювати запис, поки всі нові значення не валідовані. Не ловити `Exception` всередині моделей. Дата вводу `DD.MM.YYYY`, на диску ISO `YYYY-MM-DD`. Підтримати пробіли у тексті.

### Storage (TL: ST-01; DEV B: ST-02 після merge)

- `load_data(path: Path) -> dict`; `save_data(data: dict, path: Path) -> None`.
- `main.py` створює `AddressBook.from_dict(data['contacts'])`, `NoteBook.from_dict(data['notes'])`; callback `on_change() -> None` серіалізує обидві колекції та викликає `save_data`.
- JSON: `{"schema_version": 1, "contacts": [], "notes": []}`. Контакт — поля вище, note — `id`, `text`, `tags`. Missing file → порожні колекції; corrupt/schema mismatch → явна помилка, не перезаписувати файл; запис через temporary file + replace. Save після успішної мутації, повідомлення про success лише після успішного save. За помилки збереження повідомити, що зміни в пам'яті ще не збережено, дозволити retry, не виходити мовчки з незбереженими змінами. Тести з тимчасовим шляхом, не з реальними даними.

### Уточнення v1.0: callback, помилки збереження та dirty state

- `main.py` є єдиним власником dirty state. `on_change() -> None`: перед спробою збереження позначає стан як незбережений; після успішного запису обох колекцій скидає dirty state та повертає `None`. При невдалому записі залишає dirty state, не відкочує вже валідну мутацію в пам'яті.
- `assistant/storage.py` визначає спільний виняток `SaveError(OSError)` (без додаткових полів). `on_change` перетворює очікувані помилки запису (`OSError`, у тому числі помилки replace) на `SaveError` із зрозумілим повідомленням і збереженням причини (`raise ... from ...`). Очікувані помилки серіалізації при записі також повідомляються як помилки збереження, а не як помилки вводу; не перехоплювати всі `Exception` без розбору. Помилки load/schema/record при старті обробляються окремо, без запуску з порожніми книгами та без перезапису пошкоджених даних.
- Handlers A/B: валідна мутація → `on_change()` → `ui.success(...)` тільки якщо збереження успішне. `SaveError` не перехоплюється handlers і доходить до CLI. Помилки вводу, дублікати та невідомі ключі — `ValueError` за контрактом моделей. Повернення `False` з `on_change` не використовується.
- `main.py` передає CLI callback `has_unsaved_changes() -> bool` для читання dirty state. CLI перехоплює `SaveError` окремо від `ValueError`, повідомляє, що зміни в пам'яті не записано, пропонує `retry-save`, повертається до prompt. Не повідомляти success і не пропонувати повторно виконувати мутацію замість retry.
- `retry-save`: якщо dirty state є, викликає той самий `on_change()` без повторної мутації; успіх очищує dirty state. Якщо змін немає — нейтральне повідомлення. Подальша успішна мутація зберігає поточний стан обох книг. При `exit`/`close`/`Ctrl+C`/EOF із dirty state — явне попередження й підтвердження виходу, якщо ввід доступний; без доступного вводу не приховувати ризик втрати незбережених змін.
- SET-02: stub `SaveError`, сигнатури callback та dirty state; TL: реалізація у main (ST-01/інтеграція); DEV B: захист storage.py після ST-01 (ST-02); SM: CLI catch, retry та exit; DEV A/B: handlers за спільним контрактом. Перевірити успішний запис, невдалий запис без success, незмінність попереднього файлу, retry без повторної мутації, збереження обох книг і поведінку при виході.

### CLI (SM + DEV A/B)

- `cli.run(book, notes, on_change, *, has_unsaved_changes) -> None` (SM; keyword-only callback `has_unsaved_changes: Callable[[], bool]`). `contact_commands.get_handlers(book, on_change) -> dict[str, Callable[[], None]]` (A); `note_commands.get_handlers(notes, on_change) -> dict[str, Callable[[], None]]` (B).
- Registry SM об'єднує handlers, `help`, `exit` (alias `close`), `retry-save` за потреби. Команда вводиться окремо, handler запитує поля через `ui.prompt(label) -> str`. `ui.success(message)`, `ui.error(message)`, `ui.info(message)`, `ui.show_contacts(contacts)`, `ui.show_notes(notes)`, `ui.show_birthdays(items, *, today=None)` — shared functions (SM). Усі handlers використовують їх, не створюють власний стиль. `ui.info(message) -> None` — нейтральні повідомлення: порожня книга, немає збігів, скасування видалення, відсутність змін; `success` — успішна дія, `error` — помилка. Нейтральні повідомлення не змінюють дані.
- **Уточнення v1.0 для birthdays:** `upcoming_birthdays` зберігає формат `list[tuple[Contact, date]]`. Handler один раз визначає `today = date.today()` та передає його до `upcoming_birthdays(..., today=today, exact=...)` і `ui.show_birthdays(items, today=today)`. UI обчислює `days left = (celebration_date - today).days`; якщо `today` не передано, використовує `date.today()`. Це забезпечує узгоджені дати й відтворювані тести. Існуючі виклики `show_birthdays(items)` залишаються допустимими.
- Contact commands: `add-contact`, `list-contacts`, `edit-contact`, `delete-contact`, `find-contact`, `birthdays`. Note commands: `add-note`, `list-notes`, `edit-note`, `delete-note`, `find-note`, `add-tag`, `find-tag`, `sort-notes`. `suggestions.suggest_command(text, commands) -> str | None` (DEV A) — get_close_matches(n=1, cutoff=0.6), SM показує результат із registry, без автовиконання. Ніякої автоматичної зміни даних за fuzzy suggestion.
- `edit-contact`: порожній ввід = залишити старе; `-` очищає optional поле; ім’я змінюється лише на унікальне непорожнє. `delete-*` — підтвердження. Порожній/невідомий ввід, відсутні записи, неправильні типи — зрозуміле повідомлення, цикл триває. `Ctrl+C`/EOF — безпечне завершення з урахуванням незбережених змін.

## 4a. Продуктові правила на основі backlog v4.0

- Контакти: ім’я обов’язкове; інші поля optional. Trim для імені й адреси; порожнє optional → None. Ім’я унікальне casefold, пробіли всередині дозволені. Phone рівно 10 ASCII-цифр, str, без пробілів/плюса (локальний навчальний формат, не міжнародний стандарт). Email — базова синтаксична перевірка: один @, непорожні local/domain, крапка в домені, непорожні частини домену, без пробілів; не перевіряємо реальне існування. Birthday DD.MM.YYYY, реальна дата не в майбутньому, ISO на диску. Add/edit/load застосовують ті самі правила; invalid update не мутує дані.
- `find-contact`: критерій name або phone; name substring casefold, phone substring ASCII-цифр; порожній query відхиляється. Вивід 0/1/N у порядку книги. Birthday search окремою командою.
- `birthdays`: N — невід’ємне ціле, режим exact (default CLI) або upcoming; передати `exact=True` для exact. Exact: день народження у цільовому році припадає саме на today+N (навіть якщо N > 365); upcoming: найближчий день народження у [today, today+N], кожен контакт один раз. N=0 сьогодні; 29.02 → 28.02 у невисокосний рік (робоче правило проєкту; дата народження на диску не змінюється); без дати пропустити, overflow → ValueError. Сортувати дата, потім ім’я; показати days left.
- Нотатки — незалежна книга, не прив’язані до контактів, UUID, непорожній text після trim. Редагування зберігає id/tags. `find-note` — substring casefold лише text. Tags: comma-separated, trim/casefold, без порожніх елементів, без дублікатів. `find-tag` — exact нормалізований тег; `sort-notes` — один/кілька тегів, спочатку будь-які збіги за кількістю спадно, потім усі інші (включно без тегів); ties — порядок книги. Сортування не змінює дані. Порожній вибір → ValueError. Приклад work, urgent: [work+urgent], [work], [urgent], [home], [].
- JSON обрано як простий читабельний формат для вкладених контактів/тегів; CSV незручний для списків; pickle прив’язаний до Python-об’єктів та небезпечний для неперевірених файлів. ТЗ не обмежує формат. ST-02: DEV B редагує storage.py/test_storage.py після ST-01; TL інтегрує main та dirty state, SM підключає retry-save. Помилковий JSON/schema/record не завантажувати як пусті дані. Save failure не знищує попередній файл; не повідомляти success до save. На exit/EOF/Ctrl+C попередити про незбережені зміни; підтвердити вихід, якщо ввід доступний.
- Кожен handler викликає on_change лише після успішної мутації; read-only команди не зберігають. Спільні UI helpers відповідають за presentation, моделі не викликають input/print. Детальні AC з прикладами — у картках AB/NT/ST/CLI backlog v4.0.

## 5. Coding conventions та Definition of Done

**Ціль якості:** максимально повна та коректна реалізація вимог із ТЗ і TECH-критеріїв, обґрунтовані рішення та розуміння коду авторами. Загальні критерії «Критерії оцінювання MS in CS» (с. 1–2, рівні A/A+) використовуємо як додатковий орієнтир якості, а не нові функціональні вимоги або гарантію бала. Застосовність шкали до командного проєкту уточнюємо у ментора; правила повторної здачі домашніх завдань автоматично не переносимо.

- PEP 8; 4 spaces, snake_case для функцій/змінних, PascalCase для класів, UPPER_CASE для констант; англійські імена. line-length 79 (PEP 8), type hints для public functions, короткі docstrings для класів і неочевидної логіки. Не генерувати зайві абстракції або коментарі до очевидних рядків.
- **Конфігурація Ruff v1.0:** виконавець SET-02 фіксує однакові перевірені версії `pytest` і `ruff` у `requirements-dev.txt`; `pyproject.toml` у корені репозиторію визначає спільну конфігурацію:

  ```toml
  [tool.ruff]
  line-length = 79
  target-version = "py312"

  [tool.ruff.lint]
  select = ["E", "F", "W", "I"]
  ```

  `target-version = "py312"` відповідає мінімальній підтримуваній версії Python 3.12. `TRY004` не входить до обраного набору; для очікуваних помилок вводу/валідації у моделях зберігаємо узгоджений `ValueError`, не змінюємо його лише через lint. Не маскувати програмні помилки чи неочікуваний `TypeError`. Якщо Ruff повідомляє E501 після форматування, виправляємо довгі рядки вручну; винятки з правил лише після спільного погодження. Використовувати погоджену версію Ruff з `.venv`, а не різні глобальні інсталяції.
- Перед PR: запустити власний модуль / тест, перевірити happy path та invalid input. Обов’язкові команди після встановлення dev deps: `python -m pytest`, `python -m ruff check .`, `python -m ruff format --check .`; перед commit форматувати лише власні змінені файли, наприклад `python -m ruff format assistant/contacts.py tests/test_contacts.py` (підставити свої файли). Не запускати `ruff format .` для всього проєкту без погодження TL. Зміни конфігурації або інструментів фіксуються у спільних файлах.
- Не commit реальні контакти, data files, секрети, `.venv`, кеші. Використовувати синтетичні дані. `main` має запускатися; optional polish не блокує P0/P1.
- Перевіряти не лише власний модуль, а й сумісність із залежними модулями: imports, сигнатури, формат даних, спільні UI helpers, збереження даних. Перед PR після синхронізації з `main` повторити повний доступний набір тестів, Ruff та ручну перевірку пов’язаного сценарію. Тести мають використовувати синтетичні дані й тимчасові файли.
- Для суттєвих технічних рішень коротко пояснити причину вибору, релевантні альтернативи та компроміси (у PR або поясненні автора). Вибирати доречні засоби Python, не ускладнювати рішення заради оригінальності. Автор має вміти пояснити власний внесок, логіку, обробку помилок, обмеження та перевірки.
- Task Done: acceptance criteria пройдено, код зрозумілий автору, tests/README актуальні, PR reviewed і merged; інтегрований код у `main` перевірено після merge. Для кожного учасника — власний змістовний прийнятий PR, посилання у Trello та LMS.

## 5a. Зміни вимог та review

**Виняток для стартового baseline v1.0:** поточні уточнення DEV A та наявні defaults фіксує SM для розблокування SET-02 без очікування попереднього погодження TL. Усіх учасників повідомити про нову версію; наступні зміни контрактів проводити за звичайним порядком нижче. Незалежний review PR та перевірки залишаються обов’язковими.

Перед coding прочитати повну картку й залежні файли. Якщо запропонований AC чи контракт потребує зміни, описати в картці/Slack: поточне правило, нове правило, причина та залежні модулі. TL погоджує технічний вплив, SM фіксує AC/scope у backlog, автори залежних модулів підтверджують; TL оновлює цей файл у main. До цього не змінювати signature/schema/поведінку одноосібно. PR містить перевірку кожного AC (test або ручні steps/expected/actual), reviewer перевіряє їх; спільний Definition of Done також обов’язковий.

### AI-assisted Code Review

- Автор спочатку сам перевіряє код за AC, запускає тести та переглядає `git diff` (зокрема зміни поза своєю зоною відповідальності).
- TL (або інший учасник для PR самого TL) використовує окремий контекст AI для review: актуальний код `main`, зміни PR, погоджений CONTRIBUTING.md, картка Trello та результати перевірок. Інший AI-інструмент може бути корисним, але не є вимогою.
- Reviewer перевіряє функціональні вимоги, сумісність, валідацію, exceptions, ризик втрати даних, регресії, ООП/PEP 8, достатність тестів та необґрунтовані зміни чужих файлів. Для кожного зауваження зазначити файл/рядок (якщо доступний), проблему, вплив та мінімальне виправлення.
- Reviewer також оцінює доречність Python-концепцій, простоту й обґрунтованість суттєвих рішень, читабельність та актуальність документації. Не вимагати нових функцій або складніших підходів лише заради вищого бала.
- Critical (помилки, несумісність, втрата даних або порушення обов’язкових AC) і Major, що блокують коректну роботу, виправити до merge. Minor/polish не має затримувати реліз. Не вимагати рефакторингу без необхідності. Після виправлення повторити перевірки.
- AI-review не замінює рішення людини, запуск програми й тестів. Reviewer не схвалює PR лише на підставі відповіді AI. За нерозв’язаних технічних питань звернутися до ментора.
- Опційно TL може налаштувати GitHub Actions (`.github/workflows/ci.yml`) для встановлення погоджених залежностей, Ruff та pytest на PR і `main`, а також захист `main` з обов’язковими перевірками, якщо це не затримує розробку. Якщо CI відсутній, ті самі перевірки виконуються локально; відсутність CI не скасовує тестування.

## 6. Git workflow

1. `git clone <repo-url>` один раз. GitHub `main` — єдине джерело інтегрованого коду. Перед новою задачею перевірити `git status`; зберегти власні незавершені зміни у своїй гілці (commit або погоджений stash). На чистому робочому дереві: `git switch main`, `git pull --ff-only origin main`. Якщо pull не вдався, не продовжувати до з’ясування причини.
2. `git switch -c feature/<task-id>-short-name` (або `fix/...`). Редагувати лише погоджені файли. Не створювати нову гілку від застарілої локальної копії `main`.
3. `git status`, `git diff`, `git add <files>`, `git commit -m "AB-01: implement contact validation"`. Перед PR (і повторно, якщо `main` змінився під час review) у власній гілці з чистим робочим деревом: `git fetch origin`, `git merge origin/main`. Якщо виникли conflicts — узгодити вирішення з власником файлу; не вибирати автоматично всі свої або всі чужі зміни. За потреби незавершений merge можна скасувати через `git merge --abort`.
4. Після синхронізації оновити контекст AI, повторити тести, Ruff та ручну перевірку. `git push -u origin <branch>` для першого push гілки, далі `git push`.
5. Відкрити PR до `main`: ID задачі, зміни, як перевірено, залежності, вплив на інші модулі та потреба оновити спільні домовленості. TL review; PR самого TL перевіряє інший учасник. Якщо SM виконує SET-02 як backup, її PR також перевіряє інший учасник. Merge лише після review та успішних погоджених перевірок. Не push напряму у `main` після початкового setup, не force-push чужі гілки.
6. Після merge TL/відповідальний за інтеграцію отримує актуальний `main`, запускає застосунок, повторює автоматизовані перевірки та ключовий інтеграційний сценарій. Автор перевіряє результат своєї задачі в інтегрованій версії. У разі регресії повідомити команду, створити fix/PR; не залишати `main` у неробочому стані. Оновити Trello після підтвердження результату. Інші учасники отримують зміни перед наступною задачею або синхронізують поточну гілку за кроком 3.

Детальна покрокова інструкція для учасників — `DEVELOPMENT_WORKFLOW.md` (окремий документ). Вона доповнює, але не замінює технічні правила цього файлу.

## 7. Як працювати з AI (готова інструкція)

Перед кожною задачею забезпечити доступ AI до **актуального CONTRIBUTING.md**, AGENTS.md, DEVELOPMENT_WORKFLOW.md, вихідне ТЗ або релевантну частину, TECH-критерії, загальні критерії оцінювання MS in CS як орієнтир якості, актуальну картку Trello, актуальні файли модуля і shared contracts/skeleton з main. Для невеликого проєкту бажано надати весь актуальний вихідний код, тести та конфігурацію з власної синхронізованої гілки. Не передавати секрети чи персональні дані, `.git`, `.venv`, кеші або реальні data files. Якщо файли суперечать контракту — повідомити TL, не вигадувати новий API.

### Актуальність контексту AI

GitHub, локальний репозиторій та контекст AI — три різні рівні. Оновлення одного не гарантує оновлення інших. Перед початком задачі, після merge змін із `main` у свою гілку та перед review перевіряти актуальність файлів і версії технічного контракту. За можливості зазначити гілку й commit (`git branch --show-current`, `git rev-parse --short HEAD`); локальні незакомічені зміни враховувати окремо. У чаті без доступу до репозиторію замінити застарілі файли; у IDE/AI з доступом до GitHub перевірити, яку гілку та файли інструмент фактично бачить. AI не має припускати, що синхронізація відбулася автоматично. За відсутності доступу до коду або термінала AI просить потрібні файли/результати команд і не стверджує, що сам виконав дії.

> Ти допомагаєш реалізувати навчальний Python CLI-проєкт Personal Assistant. Використовуй цей CONTRIBUTING.md як технічний контракт (робочий baseline v1.0 та подальші зафіксовані зміни). Реалізуй тільки зазначену задачу і тільки мої файли. Збережи назви класів, методів, параметри, формат даних та shared UI. Не додавай бібліотеки, не переписуй чужі модулі без погодження. Якщо інформації бракує або контракт суперечливий, спочатку вкажи конкретний blocker. Запропонуй простий код на рівні курсу Python, з PEP 8, тестами happy path і edge cases. Поясни, як запустити, перевірити і які файли змінилися. Не стверджуй, що тести пройшли, якщо їх не запускав. Далі я самостійно перевірю код та підготую PR.

### Додаткові правила роботи з AI

**Перед реалізацією задачі:**

- Перевірити актуальність коду, CONTRIBUTING.md та вимог задачі; відрізняти робочий контракт у main від нових непогоджених пропозицій.
- Проаналізувати залежності та можливий вплив на інші задачі й модулі.
- Перевірити наявність класів, методів, функцій, параметрів та форматів результату в актуальному коді. Якщо потрібний компонент ще не реалізований, користуватися лише погодженим контрактом або skeleton/stub; не вигадувати API.
- Повідомити про суперечності, прогалини у вимогах та ризики інтеграції до написання коду.

**Під час реалізації:**

- Не змінювати погоджені контракти, спільні компоненти й чужі файли без узгодження; не дублювати наявний функціонал.
- Дотримуватися File Ownership, погоджених залежностей та формату даних. Не додавати бібліотеки без погодження.
- Писати мінімальний зрозумілий код, сумісний з актуальним застосунком; не виконувати сторонній рефакторинг.
- Якщо потрібна зміна за межами задачі, спочатку описати проблему, запропонувати рішення та вказати, кого і які файли/контракти це зачіпає. Дочекатися погодження команди за розділом 5a.

**Після реалізації задачі AI надає короткий звіт:**

- Що реалізовано та які AC покрито; що ще не виконано.
- Які файли створено/змінено та навіщо; чи є вплив на інші задачі або модулі, включно з можливими регресіями.
- Чи потрібно оновити CONTRIBUTING.md, залежності, README, тести або інші спільні файли. Якщо так — що саме і чому; якщо ні — явно зазначити це.
- Як запустити й перевірити функціонал (команди, сценарії та очікувані результати).
- Які перевірки фактично виконано та їхні результати, які лише рекомендовано або не вдалося виконати. Не вважати генерацію коду доказом працездатності.

Під час виконання задачі також керуватися `DEVELOPMENT_WORKFLOW.md`: допомагати учаснику пройти Git, синхронізацію, тестування, PR та review покроково; не виконувати незворотних дій або merge без погодження відповідального учасника.

Автор відповідає за результат: прочитати код, запустити тести, зрозуміти його до захисту. Не вставляти AI output без перевірки. Якщо ментор має окремі правила щодо AI — виконувати їх.
