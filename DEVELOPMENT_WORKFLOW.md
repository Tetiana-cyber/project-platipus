# Development Workflow

**Personal Assistant · Neoversity · v1.2 · 27.11.2026 · робоча версія**

Практична інструкція для команди з чотирьох учасників, які використовують різні AI-інструменти. Мета — не однакові відповіді AI, а один сумісний застосунок, що працює та проходить перевірки.

**Головне правило:** GitHub `main` — джерело актуального інтегрованого коду. Локальна копія та контекст AI не оновлюються автоматично лише тому, що змінився GitHub.

## 01 · Як працюємо разом

| Джерело | Що визначає |
|---|---|
| `CONTRIBUTING.md` | Технічні правила, контракти, ownership, погоджені бібліотеки. |
| `DEVELOPMENT_WORKFLOW.md` | Послідовність дій від setup до merge. |
| Trello Backlog v4.0 (або новіший) | Вимоги, Acceptance Criteria (AC), власник, статус. |
| GitHub `main` | Актуальна інтегрована реалізація. |
| Критерії оцінювання MS in CS (с. 1–2) | Додатковий орієнтир якості A/A+, не новий scope і не гарантія оцінки. |

**Статус домовленостей.** Інструкція базується на CONTRIBUTING v1.0 — робочому baseline, зафіксованому SM для розблокування SET-02. Попереднє погодження TL цього baseline не є умовою старту; зауваження опрацьовуємо окремими змінами. Після публікації джерело контракту — `main`. Команди Ruff/pytest виконуються з версіями, зафіксованими SET-02. За суперечностей повідомити команду, не вигадувати новий контракт.

**Ролі.** TL — каркас, спільні файли, review, інтеграція. Scrum Master (SM) — актуальність задач, координація і CLI. DEV A — контакти та suggestions; DEV B — нотатки, ST-02 після ST-01, README. Точний ownership — у CONTRIBUTING і Trello. Кожен учасник відповідає за власний код, тести й змістовний прийнятий PR.

Працюємо невеликими змінами: окрема гілка → реалізація → перевірки → PR → review → merge → повторна перевірка. Не чекаємо, поки всі модулі будуть завершені.

## 02 · Initial setup — Team Lead / backup SM

**До початку паралельної розробки** виконавець SET-02 (TL або backup SM) готує спільний стартовий каркас (skeleton), а не пише всі модулі самостійно.

1. Створити публічний GitHub repository, запросити учасників із правами для роботи, надіслати посилання ментору. Назву репозиторію обрати за вимогами навчального плану.
2. Використати робочий CONTRIBUTING v1.0: Python 3.12+, базовий CLI без сторонніх runtime dependencies, правила валідації, JSON та сигнатури. Додати `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md` (один рядок `@AGENTS.md`) і цей workflow у корінь репозиторію.
3. Створити структуру з CONTRIBUTING: `main.py`, `assistant/`, `tests/`, shared UI та skeleton/stubs для погоджених методів. Каркас має запускатися; тимчасові заглушки не є готовим функціоналом.
4. Додати `requirements.txt` (runtime), `requirements-dev.txt` (dev tools), `pyproject.toml`, `.gitignore`. Не включати `.venv`, кеші, секрети та реальні дані. Узгодити команду запуску і тестування.
5. Перевірити запуск каркаса у чистому середовищі. За можливості налаштувати CI (див. розділ 07), але не затримувати старт через нього. SET-02 опублікувати через PR з незалежним review відповідно до AC задачі; наступні зміни також через PR.
6. Повідомити команду: URL репозиторію, версія Python, актуальний commit, робочий CONTRIBUTING v1.0, готовність до роботи. Кожен клонує саме цей репозиторій.

### Контрольна точка: можна починати

- [ ] Репозиторій доступний усім чотирьом учасникам.
- [ ] Є робочий контракт, структура файлів та їхні власники.
- [ ] Є робоча команда запуску каркаса та перелік залежностей.
- [ ] Усі розуміють, які файли змінюють; залежності між задачами погоджені.

**Важлива залежність:** DEV B починає ST-02 після merge ST-01 від TL. Якщо інший модуль ще не готовий, використовуйте лише погоджені сигнатури/stubs. Не створюйте паралельну версію чужого модуля.

## 03 · Initial setup — кожен учасник

Відкрити Terminal у VS Code. Команди виконувати у папці для навчальних проєктів, а після clone — в корені спільного репозиторію. Замінити позначки `<...>` на реальні значення (не копіювати кутові дужки).

```bash
git clone <repo-url>
cd <repo-folder>
git status
git remote -v
```

`clone` потрібен лише один раз. Якщо вже клонували правильний репозиторій, просто відкрийте його папку. Не робіть `git init` і не створюйте власний окремий repo. `git remote -v` має показати спільний GitHub URL.

### Python і virtual environment

Перевірте `python --version` (на macOS до активації може знадобитися `python3 --version`). Використайте Python 3.12+; SET-02 фіксує перевірену версію середовища. Створіть своє локальне середовище `.venv`:

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

**Windows (PowerShell)**

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Якщо команда `py`/`python3` запускає не ту версію, використайте відповідний Python interpreter. У VS Code оберіть `.venv` через Python: Select Interpreter. Якщо PowerShell блокує активацію, використайте `.venv\Scripts\python.exe` замість `python` або попросіть AI допомогти без вимкнення системного захисту.

```bash
python --version
python -m pip install -r requirements.txt
python -m pip install -r requirements-dev.txt
python main.py
```

Встановлюйте dev dependencies лише з погодженого файлу. Якщо requirements або команда запуску відрізняються, використовуйте затверджені TL інструкції. Вийдіть із застосунку командою `exit` (коли реалізована). На цьому етапі важливо, щоб каркас запускався без import errors.

## 04 · Початок кожної задачі

**1. Відкрити картку Trello.** Прочитати очікувану поведінку, технічний опис, AC, залежності та ownership. Перевести задачу в In Progress. Перевірити, чи готові залежності.

**2. Отримати актуальний код.** Перед переходом між гілками перевірити `git status`. Якщо є незавершені зміни, зберегти їх у власній гілці (commit або погоджений stash). Не переносити випадково зміни в `main`.

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c feature/AB-01-contact-models
```

Приклад назви гілки: `feature/AB-01-contact-models`. Замініть ID і назву на свою задачу. Якщо гілка вже існує, використовуйте `git switch <branch>` і синхронізацію з розділу 06. Якщо pull не вдався, зупиніться й з'ясуйте причину разом з TL; не застосовуйте примусові команди.

**3. Перевірити, яку версію коду бачить AI.**

```bash
git branch --show-current
git rev-parse --short HEAD
git status
```

Назва гілки та commit допомагають ідентифікувати версію; незакомічені зміни вказуйте окремо.

| Тип AI | Як надати контекст |
|---|---|
| Чат / AI Project | Завантажити актуальні файли з робочої гілки; замінити старі копії. |
| AI в IDE | Відкрити корінь repo, перевірити branch і доступ до файлів. |
| AI з GitHub access | Переконатися, що бачить потрібний repo, branch і commit; локальні зміни може не бачити. |

Забезпечити доступ AI до AGENTS.md, CONTRIBUTING.md, DEVELOPMENT_WORKFLOW.md, ТЗ, TECH-критеріїв, загальних критеріїв оцінювання MS in CS, актуальної картки Trello та коду/тестів/конфігурації. Файли з відкритого repo окремо не завантажувати; документи поза repo надати в контексті AI. Для цього невеликого проєкту бажано надати весь актуальний source code. Не передавати `.git`, `.venv`, кеші, секрети чи справжні персональні дані.

## 05 · Development & local testing

**4. Проаналізувати задачу з AI.** Попросити перевірити AC, залежності, наявні класи й методи, можливий вплив на інші модулі. Якщо потрібний компонент відсутній, користуватися погодженим skeleton, а не вигадувати API.

**5. Реалізувати лише свою задачу.** AI може генерувати код або пропонувати зміни, але автор читає їх та розуміє логіку. Для суттєвих рішень попросити AI коротко пояснити вибір, альтернативи та обмеження; автор має бути готовий пояснити реалізацію й перевірки на захисті. Не дозволяйте AI переписувати чужі файли, додавати бібліотеки, міняти JSON schema або сигнатури без погодження.

> Якщо потрібні зміни контракту: у Trello/Slack описати поточне правило, пропозицію, причину й залежні модулі. TL погоджує технічний вплив, SM оновлює AC, власники залежних модулів підтверджують, TL оновлює CONTRIBUTING у `main`. Лише потім реалізовувати зміни.

**6. Перевірити результат.** Перетворити кожен AC на тест або ручний сценарій. Використовувати вигадані контакти й нотатки, а для автоматизованих тестів — тимчасові файли, не справжній data.json.

| Рівень | Приклад перевірки |
|---|---|
| Unit | Валідний телефон приймається, невалідний відхиляється. |
| Integration | Контакт, створений через handler, потрапляє до AddressBook і зберігається через storage. |
| Manual / end-to-end | Додати запис, перезапустити CLI, перевірити запис, відредагувати й видалити; помилки вводу не завершують програму. |

```bash
python -m pytest
python -m ruff check .
python -m ruff format --check .
```

Запустіть усі три перевірки з версіями, зафіксованими SET-02. Для форматування лише своїх файлів (приклад):

```bash
python -m ruff format assistant/contacts.py tests/test_contacts.py
```

Не запускайте `ruff format .` без погодження TL. Якщо перевірка не пройшла — прочитайте помилку, виправте й повторіть. Якщо тест не запускався, не позначайте його як passed. AI може допомогти розібрати output, але факт виконання підтверджує термінал/CI.

## 06 · Commit, synchronization & Pull Request

**7. Зберегти зміни у власній гілці.** Перевірити список змінених файлів і diff. Додавати до commit лише файли задачі (приклад для AB-01).

```bash
git status
git diff
git add assistant/contacts.py tests/test_contacts.py
git diff --cached
git commit -m "AB-01: implement contact models"
```

**8. Синхронізуватися з `main` перед PR.** Переконатися, що ви у своїй feature-гілці й робоче дерево чисте. Не переходити в `main` для цієї операції.

```bash
git branch --show-current
git status
git fetch origin
git merge origin/main
```

`fetch` отримує актуальні зміни GitHub; `merge origin/main` додає їх у вашу гілку. Якщо main змінився під час review, повторити цей крок. Після синхронізації оновити контекст AI та повторити всі погоджені тести, Ruff і ручну перевірку.

**9. Push та PR.** Перший push гілки (підставте свою назву), наступні push — без `-u`.

```bash
git push -u origin feature/AB-01-contact-models
```

На GitHub обрати Pull requests → New pull request: base = `main`, compare = ваша feature-гілка. Перевірити Files changed, додати опис, запросити TL (для PR TL — іншого учасника). В Trello додати посилання та статус Review/QA. Push сам по собі не означає, що зміни прийнято.

### Шаблон опису PR

- **Task:** ID + посилання на Trello.
- **Changes:** що реалізовано та які файли змінено.
- **Acceptance Criteria:** для кожного AC — тест або steps / expected / actual; зазначити незавершене.
- **Checks:** фактично виконані команди, результат; що не перевірено.
- **Impact:** залежні модулі, зміни контракту/бібліотек/README; якщо немає — явно зазначити.
- **Key decisions:** коротке обґрунтування суттєвих технічних рішень; якщо таких немає, додаткове обґрунтування не потрібне.

**Не push напряму в `main` після setup.** Не force-push чужі гілки, не merge власний PR без незалежного review.

### Контрольна точка: Ready for Review

Після створення PR та успішних перевірок AI автора зупиняється перед merge, повідомляє наступний крок, вказує reviewer, готує коротке повідомлення з ID задачі, посиланнями на Trello і PR та результатами перевірок. Автор запрошує reviewer у GitHub, переводить картку в Review і передає повідомлення (AI допомагає за наявності доступу). Reviewer відкриває окрему AI-сесію та передає актуальний PR і картку. Якщо немає блокуючих зауважень, після погодження людини переходять до merge; інакше автор виправляє їх у тій самій гілці.

## 07 · Code Review, merge & integration

**Reviewer:** TL; PR самого TL перевіряє інший учасник. Використати окремий AI-контекст для review (інший AI може допомогти, але не обов'язковий). Передати актуальний `main`, зміни PR, затверджений CONTRIBUTING, AC та результати тестів. На GitHub Files changed — diff, тобто які саме рядки змінено.

> Попросіть AI перевірити відповідність AC, imports та сигнатури, формат даних, валідацію, exceptions, ризик втрати даних, можливі регресії, OOP/PEP 8, тести та зміни чужих файлів. Для кожного зауваження — файл/рядок, проблема, вплив і мінімальне виправлення. Також перевірити доречність Python-концепцій, простоту, обґрунтованість суттєвих рішень та актуальність документації. Не вимагати зайвого рефакторингу.

| Рішення review | Дія |
|---|---|
| Critical / Major, що блокує роботу | Автор виправляє, повторює перевірки та push у ту саму гілку; PR оновлюється. |
| Minor / polish | Не затримувати реліз; за потреби зафіксувати окремо. |
| Перевірки успішні, reviewer погодив | Можна merge після перевірки актуальності гілки. |

TL або відповідальний за інтеграцію об'єднує PR з `main` через GitHub. Якщо налаштовано GitHub Actions, перевіряє успішність CI. CI опціональний: без нього обов'язково виконати ті самі погоджені перевірки локально. AI-review не замінює рішення людини.

### Після merge — не пропускати

```bash
git status
git switch main
git pull --ff-only origin main
python -m pytest
python -m ruff check .
python -m ruff format --check .
python main.py
```

TL перевіряє ключовий інтеграційний сценарій; автор перевіряє свій функціонал у `main`. При зміні залежностей перевстановити їх з погоджених requirements. Якщо виникла регресія — повідомити команду, створити fix/PR, за потреби узгодити відкат із TL. Не залишати `main` неробочим. Тільки після підтвердження результату — Done у Trello. Зберегти посилання на власний accepted PR для LMS.

### Фінальний QA та підготовка до захисту

У межах QA-02 (після QA-01 і фіналізації README) SM за допомогою окремого AI-контексту проводить комплексну оцінку конкретного RC/commit: покриття ТЗ/TECH, коректність, якість коду, обґрунтованість рішень, надійність, тести й документацію. Вказати фактичні докази, неперевірене, сильні сторони, блокуючі проблеми й неблокуючі покращення. Використовувати A/A+ як орієнтир, а не прогноз або гарантію бала. Не затримувати реліз через необов’язковий polish. У REL-01 кожен учасник готує коротке пояснення власного внеску, Python-концепцій, ключових рішень та перевірок; це не потребує розширення demo понад погоджений час.

## 08 · Troubleshooting — якщо щось пішло не так

| Ситуація | Що робити |
|---|---|
| AI посилається на неіснуючу функцію | Перевірити actual code / контракт, оновити AI context. Не створювати дубль. |
| ImportError / ModuleNotFoundError | Перевірити корінь repo, `.venv`, requirements, назву модуля та чи виконано merge залежності. |
| Git не дозволяє switch або pull | Прочитати `git status`. Зберегти власні зміни у своїй гілці; звернутися до TL при незрозумілому стані. |
| Тести не проходять | Надати AI точний output, файли й commit; відтворити помилку. Не видаляти тест, щоб отримати зелений статус. |
| GitHub відхиляє push | Перевірити URL, права доступу, гілку та повідомлення. Не обходити захист `main`. |
| AI змінив чужі файли | Переглянути diff; погодити потрібні зміни з власником, не додавати випадкові зміни до PR. |

### Merge conflict: покроково

Конфлікт означає, що Git не може автоматично об'єднати зміни в одному місці. Це не обов'язково помилка коду.

1. Виконати `git status` і визначити conflicted files. Не починати інший merge або pull.
2. Відкрити файли у VS Code, переглянути обидві версії. Передати AI контекст конфлікту, AC та зміни обох сторін. Узгодити результат із власником файлу/TL; не натискати Accept All Current/Incoming навмання.
3. Зберегти коректно об'єднаний файл без conflict markers. Виконати `git add <resolved-files>`, `git status`, а після розв'язання всіх конфліктів — `git commit` (завершення merge). Повторити тести та push своєї гілки.
4. Якщо не зрозуміло, як об'єднати, можна скасувати незавершений merge через `git merge --abort`, якщо починали його з чистим робочим деревом; звернутися до TL. Не використовувати `git reset --hard` чи force-push як швидке виправлення.

**Як просити допомогу:** ID задачі, гілка/commit, команда, повний текст помилки, що вже спробували, які файли зачеплено. Технічні блокери — TL; нерозв'язані командою питання — ментору.

Використовуйте цей список для кожної задачі. Якщо AI не має доступу до термінала або репозиторію, він пояснює крок і просить надіслати результат; не стверджує, що виконав дію сам.

- [ ] Прочитано картку Trello, AC, залежності й актуальний CONTRIBUTING.
- [ ] Отримано актуальний `main`; створено або синхронізовано власну feature-гілку.
- [ ] AI бачить актуальний код, AGENTS.md, CONTRIBUTING.md, DEVELOPMENT_WORKFLOW.md та потрібні вимоги.
- [ ] Перевірено вплив на інші задачі; необхідні зміни погоджено.
- [ ] Реалізовано лише погоджений scope, автор розуміє код та може пояснити суттєві рішення.
- [ ] Усі AC перевірено; тести, Ruff та ручні сценарії виконано за погодженими правилами.
- [ ] Переглянуто diff, створено commit; робочу гілку синхронізовано з `main` і перевірено повторно.
- [ ] Створено PR з описом змін, перевірок і впливу; reviewer отримав посилання, проведено незалежний review.
- [ ] Зауваження виправлено; PR прийнято та merged.
- [ ] Після merge інтегрована версія перевірена, Trello оновлено; посилання на PR збережено.
