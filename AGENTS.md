# Personal Assistant — Agent Instructions

Спільні інструкції для Codex, Claude Code, Kiro та інших AI coding agents. Застосовуються до всього репозиторію. Учасники команди не мають професійного досвіду програмування: пояснюй рішення та необхідні дії зрозуміло, без зайвої теорії.

## 1. Обов'язковий контекст

Перед початком кожної задачі прочитай актуальні файли з кореня репозиторію:

- `CONTRIBUTING.md` — технічний стандарт, архітектура, контракти, File Ownership, правила якості та роботи з AI.
- `DEVELOPMENT_WORKFLOW.md` — послідовність роботи з Git, тестуванням, Pull Requests, Code Review та інтеграцією.

Також враховуй оригінальне ТЗ Neoversity, TECH-критерії та повний опис відповідної задачі з актуального Trello Backlog / Trello, включно з Acceptance Criteria (AC). Якщо вони недоступні, попроси користувача надати потрібний контекст; не вигадуй вимоги за одним ID задачі. Не трактуй draft або TBD як затверджені рішення. Якщо документи, вимоги та код суперечать одне одному, повідом про це перед реалізацією і запропонуй рішення для погодження.

Враховуй загальні критерії «Критерії оцінювання MS in CS» (с. 1–2, A/A+) як додатковий орієнтир якості. Вони не змінюють ТЗ, TECH, погоджений scope чи контракти. Якщо документа немає в контексті, керуйся принципами якості з CONTRIBUTING.md та повідом про обмеження під час фінальної оцінки; не вигадуй бал.

## 2. Перед реалізацією

- Перевір корінь репозиторію, `git status`, поточну гілку та commit, актуальність `origin/main` і наявність локальних змін. Дотримуйся workflow синхронізації; не вважай локальний код автоматично актуальним.
- Визнач ID задачі, її межі, власника файлів, залежності та можливий вплив на інші модулі. Перевір фактичні сигнатури та спільні контракти в коді; якщо залежний модуль ще не готовий, використовуй лише погоджений skeleton/contract.
- Коротко поясни запропонований підхід, blockers та питання, які потребують погодження. Для суттєвих рішень поясни, чому обраний підхід доречний, які релевантні альтернативи та компроміси існують. Якщо потрібні зміни спільних контрактів або чужих файлів, дочекайся погодження відповідальних учасників.

## 3. Реалізація та Git

- Виконуй лише поточну задачу у відповідній feature/fix branch. Зберігай наявні зміни користувача та інших учасників.
- Дотримуйся затверджених назв файлів, класів, методів, параметрів, форматів даних, залежностей і стилю CLI. Пиши простий, читабельний Python відповідно до PEP 8 та погоджених принципів ООП.
- Не додавай бібліотеки, не змінюй архітектуру, shared contracts, чужі модулі чи спільну документацію без погодження. Не виконуй сторонній рефакторинг і не дублюй наявний функціонал. Автоматично створені specs, steering files чи локальні правила не можуть замінювати погоджені вимоги команди.
- За наявності доступу та дозволів допомагай виконувати технічні дії: читання і редагування файлів, створення робочої гілки, синхронізацію, запуск застосунку та тестів. Перед commit, push, створенням PR або merge отримай погодження користувача; merge PR — лише за правилами review команди. Не push напряму в `main` після початкового setup. Не використовуй force-push, `git reset --hard`, видалення чужих змін чи інші руйнівні операції як спосіб вирішити проблему. За конфлікту зупинись, поясни його та узгодь рішення.
- Не передавай і не додавай у Git секрети, реальні персональні дані, локальні data files, `.venv` чи кеші. Для тестів використовуй синтетичні дані та тимчасові файли.

## 4. Перевірка та review

- Перевір усі AC, happy path, edge cases, обробку помилок і можливі регресії. Додай або онови релевантні тести.
- Запусти погоджені перевірки (pytest, Ruff, інтеграційні та ручні сценарії згідно з документами). Форматуй тільки власні змінені файли. Переглянь Git diff, включно з новими файлами, та перевір, що зміни не виходять за scope.
- Перед PR синхронізуй робочу гілку з `main` за погодженим workflow та повтори перевірки. Після merge перевір інтегровану версію відповідно до ролі учасника.
- Під час Code Review перевір вимоги, сумісність, безпеку збереження даних, тести та регресії; вказуй конкретну проблему, її вплив, пріоритет та мінімальне виправлення. Не схвалюй PR замість людини. Не стверджуй, що перевірки пройшли, якщо їх фактично не виконано.

### Передача задачі на Code Review

- Після погодженого створення PR та успішних перевірок зупинись перед merge. Явно повідом про готовність до незалежного review, вкажи reviewer згідно з DEVELOPMENT_WORKFLOW.md, посилання на PR і картку Trello, підготуй коротке повідомлення reviewer.
- Допоможи запросити reviewer у GitHub і перевести картку в Review за наявності доступу та погодження; інакше поясни ручні дії. Не вважай review виконаним лише через створення PR чи власну перевірку. Продовжуй до merge лише після незалежного review, усунення блокуючих зауважень, повторних перевірок і погодження відповідального учасника.
- У ролі reviewer працюй в окремому контексті; перевір актуальний PR, AC, контракти, фактичні тести, якість і обґрунтованість суттєвих рішень. Надай рекомендацію Approve / Request Changes з поясненням, не схвалюй PR замість людини.

## 5. Підсумок задачі

Надай короткий звіт:

- Що реалізовано, які AC покрито та що залишилося невиконаним.
- Які файли змінено і навіщо.
- Чому обрані суттєві технічні рішення доречні; поясни автору логіку, використані Python-концепції, обмеження та edge cases так, щоб він міг самостійно пояснити свій внесок під час захисту. Не ускладнюй прості рішення заради демонстрації майстерності.
- Які залежності, ризики або вплив на інші задачі виявлено.
- Чи потрібно оновити `CONTRIBUTING.md`, backlog, README, залежності або інші спільні файли; якщо так — що саме та чому.
- Як запустити застосунок і перевірити результат; фактичні результати тестів та перевірки, які не виконано.
- Який наступний крок відповідно до `DEVELOPMENT_WORKFLOW.md`.

Для QA-02 допоможи виконати комплексну незалежну оцінку конкретного RC/commit за офіційними вимогами та орієнтирами A/A+. Відокремлюй невиконані вимоги, дефекти, неблокуючі покращення та неперевірені припущення. Для REL-01 допоможи кожному учаснику підготувати пояснення власного внеску. Не гарантуй оцінку ментора.

Якщо немає доступу до файлів, Git, термінала чи потрібних дозволів, повідом про обмеження і надай користувачу конкретні кроки. Не імітуй виконання дій. Автор задачі та відповідальний reviewer залишаються відповідальними за перевірку результату й погодження змін.
